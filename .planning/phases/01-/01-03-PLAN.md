Add public async method to ChannelManager following lock-minimizing pattern from RESEARCH.md Pattern 3 (lines 143-192).

**Method signature:**
```rust
pub async fn update_coinbase_and_broadcast(
    &self,
    new_address: &str,
    user_id: String,
) -> Result<(), PoolError<error::ChannelManager>>
```

**Implementation - Four phase pattern (CRITICAL for deadlock prevention):**

**Phase 1 - Validate address (before any locks):**
- Call validate_and_parse_address(new_address, Network::Regtest)
- Return early with descriptive error if validation fails (API-02)

**Phase 2 - Read template state (short lock):**
- Acquire channel_manager_data lock using super_safe_lock
- Clone last_future_template (needed for job recreation)
- Extract current coinbase_outputs
- Release lock immediately

**Phase 3 - Compute new coinbase outputs (NO locks held):**
- Deserialize current coinbase using deserialize_outputs helper
- Replace output address with new validated scriptPubKey
- Keep same value (don't modify amount - only address changes)
- Serialize back to bytes

**Phase 4 - Atomic state update and job distribution (short locks):**
- Acquire channel_manager_data lock
- Update coinbase_outputs field with new serialized outputs
- Iterate downstreams, collect (downstream_id, downstream) pairs
- Release channel_manager_data lock BEFORE acquiring downstream locks
- For each downstream:
  - Acquire downstream_data lock
  - Call job recreation logic (reuse pattern from template_distribution_message_handler.rs lines 218-236)
  - Collect NewMiningJob messages for standard channels
  - Release downstream_data lock
- Collect all messages outside locks

**Phase 5 - Broadcast (no locks, all I/O):**
- For each message, call message.forward(&channel_manager_channel).await
- Return Ok(()) on success

**CRITICAL - Lock ordering discipline (prevents Pitfall 1):**
- NEVER acquire downstream_data while holding channel_manager_data
- Clone downstream collection BEFORE iterating
- Keep all lock hold times under 50μs (compute outside locks)

Follow exact pattern from template_distribution_message_handler.rs for job recreation. Reuse requires_standard_jobs check, get_active_job pattern, NewMiningJob construction.

**Why user_id parameter:** Phase 2 will use this for share attribution. Store in ChannelManager for now (add field to ChannelManagerData if needed), but don't implement attribution yet.
